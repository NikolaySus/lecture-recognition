# GigaAM: динамические пропорции каналов

Независимая серия: Energy, SNR-proxy и EV-normalized, каждый в fast/slow,
для RNNT greedy (основа RNNT left) и CTC beam=32/bias_weight=4
(основа CTC combination). Всего 12 новых вариантов и пять импортированных
сравнений: исходные CTC/RNNT, RNNT left, CTC combination, CTC bias4.
Все успешные варианты включаются независимо от Парето или WER.

## Методика

Префикс 345,92 с декодируется в стерео 16 кГц. Кадры Hamming 30 мс,
шаг 10 мс, обновление весов 100 мс. Energy — средняя мощность;
SNR-proxy — max(mean(E) − N, 0)/max(N, 1e-12), где N — десятый
процентиль энергии предыдущих 20 с; EV-normalized — средняя по 20
mel-полосам дисперсия E^(1/3), делённая на квадрат среднего.
Это адаптация EV с нормализацией масштаба, а SNR — приближение без VAD.

Fast: признаки за последнюю секунду, постоянная сглаживания 0,3 с.
Slow: признаки за 3 с, сглаживание 1 с. Целевой левый вес qL/(qL+qR),
при обеих нулевых оценках 0,5. Начальный вес 0,5; экспоненциальное
сглаживание, затем линейная интерполяция между обновлениями. В тишине
ниже −60 dBFS веса замораживаются. Если один канал нулевой, целевой
вес ненулевого равен единице. Для файла доступен будущий вес точки
интерполяции; первая серия офлайн, не обещает нулевую потоковую задержку.

Итог: wL·L+(1−wL)·R. Нет усиления, коррекции задержки, полярности,
шумоподавления или дообучения. Смесь вычисляется до нарезки чанков,
поэтому перекрытия получают одинаковые значения. Исключённые кадры
не участвуют в признаках, исключённые аудиоинтервалы обнулены в смеси.
Диагностика сохраняет веса, оценки, корреляцию и ослабление относительно
суммы мощностей взвешенных каналов; ослабление более 3 dB отмечается.
Ослабление — диагностический индикатор, не оценка WER.

Симметрия проверяется на каждой подготовленной смеси: после перестановки
каналов максимальная разность отсчётов ≤1e-7, сумма соответствующих
левых весов отличается от единицы ≤1e-12. Это не заменяет будущие
эталоны реальных участков с лучшим правым каналом.

## Запуск и продолжение

```bash
.venv/bin/python scripts/benchmark_dynamic_channels.py prepare
.venv/bin/python scripts/benchmark_dynamic_channels.py run
.venv/bin/python scripts/benchmark_dynamic_channels.py progress
.venv/bin/python scripts/benchmark_dynamic_channels.py report
```

`--retry-failed` повторяет ошибочные случаи; успешно завершённые случаи
и чанки сохраняются. `--source` задаёт проверенную пересборку предыдущей
серии, по умолчанию берётся её `latest-report.json`. Новый кеш:
`.lecture-cache/gigaam-dynamic-channels/<hash>`, собственный `latest.json`.
Изменение исходников алгоритма, ревизий, параметров, эталона или входных
данных создаёт другую серию. Запуск GPU последовательный. Прогресс —
доля завершённых чанков ASR и выравнивания, не оценка оставшегося времени.

Импорт проверяет хеши записи, эталона, исторического моноаудио и версии
обработки; сохранённые оценки пяти сравнений повторно вычисляются из
слов и обязаны совпасть. Их исходные файлы не меняются.
Для новых вариантов сохраняются сырые чанки ASR, кеш выравнивания,
аудит склейки, SRT, WER v2/v1 и время обработки. Границы чанков,
общее моноаудио выравнивания и склейка совпадают с предыдущей серией.
Общий WER вычисляется по трём объединённым группам, а не суммой карточек.

Отчёт: `output/pdf/r001-r008-gigaam-dynamic-channels.pdf`, рядом JSON
с результатами и хешами. Завершённая таблица содержит 17 колонок моделей,
упорядоченных по убыванию общего WER. Сохранены цветовая шкала и жирное
выделение лучших результатов. Приложение включает параметры, статус
каждого варианта, сравнение со своей фиксированной основой и графики
весов. В предварительном PDF невыполненные варианты перечислены в
приложении; вымышленных транскрипций в таблице нет. Прежний PDF сохранён.

В текущем окружении CUDA не доступна: попытка `run` не запустила ASR.
Подготовлены смеси и очередь из 12 вариантов; результаты динамического
распознавания пока отсутствуют. Повторы ASR и сдвиги границ не входят
в эту серию. После восстановления CUDA достаточно повторить `run`,
затем `report`.

## Пилот R005: порог и крутизна кривой

Следующий этап реализован отдельно, без PDF и без автоматического
запуска полного тестирования. Energy и EV-normalized, каждый fast/slow,
пороги 60–67% с шагом 1%, k=2/4/8, две модели: **192 конфигурации**.

Кривая применяется после прежнего сглаживания и интерполяции каждого
отсчёта. Для a=max(w,1−w), порога t и u=(a−t)/(1−t): при a≤t вес
не меняется, иначе a′=1−(1−a)·exp(−k·u²). Обработка симметрична по
каналам, плавна на пороге, не вводит усиления сигнала. Базовые веса
берутся из сохранённой предыдущей серии, их файлы входят в хеши источников.

```bash
.venv/bin/python scripts/benchmark_channel_curves.py prepare
.venv/bin/python scripts/benchmark_channel_curves.py run
.venv/bin/python scripts/benchmark_channel_curves.py progress
.venv/bin/python scripts/benchmark_channel_curves.py select
```

`--retry-failed` повторяет ошибочные случаи. Новый кеш:
`.lecture-cache/gigaam-channel-curves-r005/<hash>`, собственный `latest.json`.
Подготовлены 96 смесей для совместного использования CTC и RNNT.
PCM хранится от начала записи до 186,64 с, сохраняя абсолютные координаты;
признаки и сглаживание используют прежнюю историю и не сбрасываются на R005.

Для ASR запускаются только чанки №10 и №11: 153,55–171,01 и
169,01–186,64 с. Декодеры наследуются от RNNT left и CTC combination.
Два выравнивания подставляются в сохранённый контекст своей основы.
Для назначения границ используется прежнее текстовое сопоставление
объединённого участка, но публикуется только оценка R005. Общий WER
гибридной записи не используется. Входные транскрипции ASR не содержат
эталона. Контроль RNNT left воспроизведён: **2/27, WER 7,41%**.

Общий кеш чанков учитывает хеш фактических входных отсчётов, настройки
декодера и границы; одинаковые чанки повторно не распознаются.
Все конфигурации остаются отдельными записями, даже при одинаковом
аудио/тексте. Прогресс учитывает 768 логических шагов ASR/выравнивания
и отдельно число уникальных завершённых ASR-чанков.

Выходы: `results.json`, `shortlist.json`, `summary.txt`, `controls.json`.
В диагностике аудио записаны веса до/после кривой, средняя/минимальная/
максимальная доля левого канала в R005 и доля выше 80/90%.
Кандидаты сортируются по ошибкам R005, CER, убыванию порога, возрастанию
k и названию. Отбирается общий топ-10 плюс все варианты не хуже RNNT left;
список может быть длиннее десяти. При ошибках или незавершённых случаях
он помечается предварительным. Полное тестирование — отдельный следующий
этап: результаты отбора на R005 не доказывают переносимость на R001–R008.

Подготовка и проверки завершены, но текущая попытка GPU-запуска
остановилась из-за недоступной CUDA; новых пилотных результатов пока нет.
После восстановления CUDA повторить `run`, затем `select`.
Прошли 130 профильных тестов, Ruff и проверка пробелов в diff.

Для будущего полного тестирования исправлена потеря «процент» при правой
копии «спроцент». Восстановление требует полного слова слева и двух
независимых опор по времени/тексту, без эталона. Аудит 57 сохранённых
случаев: только два CTC EV улучшились с 28 до 27 ошибок, остальные оценки
не изменились; R005 неизменён у всех. Доказательства:
`output/pilot-prefix-recovery-audit.json`. Прежние PDF и исходные результаты
не перезаписывались. Для полного отчёта все сравнения необходимо
пересчитать по новой версии склейки.

## Новая серия с пониженными порогами

Сетка `lower`: **52, 54, 56, 58, 60%**, **k=2/4/8/16**,
Energy и EV-normalized, каждый fast/slow. Порог 50% исключён.
Это 80 смесей и 160 конфигураций для CTC combination и RNNT left.
Сетка `legacy` сохраняет пороги 60–67% и k=2/4/8 (192 конфигурации).
Диагностика и пилот используют общую декларацию сеток; по умолчанию — `lower`.

```bash
.venv/bin/python scripts/analyze_channel_curve_weights.py --grid lower
.venv/bin/python scripts/benchmark_channel_curves.py prepare --grid lower
.venv/bin/python scripts/benchmark_channel_curves.py run --grid lower
.venv/bin/python scripts/benchmark_channel_curves.py progress
# После ошибок, для той же сетки и источников:
.venv/bin/python scripts/benchmark_channel_curves.py run --grid lower --retry-failed
```

Диагностика: `output/channel-curves-r005-weights.json` и `.csv`.
Использованы базовые веса динамической серии с интерполяцией на частоте
16 кГц в точном окне R005. Сохранены средний, минимум и максимум левого
веса, время выше 80/90% для обоих каналов, доля изменённых отсчётов
и усиления правого канала. Хеши источников и параметры записаны в JSON.

При t52/k16 Energy fast достигает 90,37% слева и проводит 10,39% R005
выше 80%; EV fast достигает 93,34% и проводит 6,81% выше 80%.
Это усиление относительно k8, но улучшение WER требует ASR.

Пилот оценивает только R005 через замену двух чанков и проекцию текстового
выравнивания группы на карточку; соседний контекст заморожен.
Пять контролей и знаменатель 27 слов сохраняются. RNNT left — 2/27.
Общий WER гибридного контекста не публикуется. PDF и полный прогон
R001–R008 не запускаются автоматически.

Серия получает отдельный каталог по хешу параметров и источников,
предыдущие артефакты не перезаписываются. `latest.json` указывает на
последнюю подготовленную серию, и команда `progress` читает именно её.
Для новой сетки прогресс считается из 320 пар «конфигурация–чанк» и
640 логических этапов; идентичные входы используют общий кэш.

Отбор: общий топ-10 плюс все варианты не хуже RNNT left. Порядок —
число ошибок, CER, порог по убыванию, k по возрастанию, название.
`shortlist.json` содержит группы `quality_ties`: равные ошибки и CER
означают равное измеренное качество, порядок внутри них служебный.
До успешного завершения всех 160 конфигураций отбор предварительный.

Диагностика всех 80 смесей рассчитана. В среде агента PyTorch сообщает
`torch.cuda.is_available() == False`; ASR требует запуска в среде
с доступной CUDA. Подготовка PCM и контрольных оценок выполняется на CPU.

## Полная проверка Energy fast t52/k32

Отдельная серия сравнивает две новые конфигурации с пятью контролями:
исходные CTC/RNNT, RNNT left, CTC combination и CTC bias4. Полный префикс
0–345,92 с, 22 исторических чанка на модель; все семь вариантов остаются
в таблице. Метрики пилота не подставляются в полный результат.

```bash
.venv/bin/python scripts/benchmark_channel_curve_full.py prepare
.venv/bin/python scripts/benchmark_channel_curve_full.py run
.venv/bin/python scripts/benchmark_channel_curve_full.py progress
.venv/bin/python scripts/benchmark_channel_curve_full.py run --retry-failed
.venv/bin/python scripts/benchmark_channel_curve_full.py report
```

По умолчанию используется завершённый пилот из его `latest.json`;
для явной фиксации источника передайте `--pilot PATH`. Новая серия хранится
в `.lecture-cache/gigaam-channel-curve-full/<hash>`, с отдельным указателем.
Параметры, источники и код входят в идентификатор серии. Проверяются
неизменность записи, эталона, кода обработки и окружения пилота.

Полная PCM-смесь побайтово сверяется с пилотным префиксом. Четыре
готовых чанка (по два на модель) копируются в кэш только при совпадении
PCM, декодера и границ. Подготовка даёт 8 из 88 логических этапов
(9,1%); остаётся распознавание и выравнивание 40 чанков.
Пять контролей пересобираются из исходных поканковых выравниваний.
Аудит сохранён в `control-rescore-audit.json`; текущий пересчёт не изменил
их оценки. После завершения проверяется полное совпадение оценки R005
с пилотом; расхождение блокирует выпуск финального отчёта.

Отчёт создаётся автоматически после успешного `run`, либо отдельно
командой `report`: `output/pdf/r001-r008-gigaam-energy-fast-t52-k32.pdf`
и одноимённый JSON. Незавершённая серия не выдаётся за финальный отчёт.
Таблица содержит ID, время, семь конфигураций и эталон. Порядок —
по убыванию общего WER; лучшие результаты каждой строки выделены
жирным, ячейки окрашены по WER. Приложение показывает изменения
относительно родителей, сырые ответы R004/R005 и графики весов до/после
кривой. В `focus-audit.json` и `pilot-r005-check.json` сохранены проверки.

Общий WER считается по трём объединённым группам (246 слов), карточки
оцениваются проекцией текстового выравнивания. Настройка выбрана на R005,
поэтому проверка остальных карточек той же записи не является
независимым тестом. При недоступной CUDA подготовка и контрольный
пересчёт работают на CPU; новый ASR не начинается.
