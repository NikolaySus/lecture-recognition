# MCP pivot: архитектура и статус

Исследовательская база закреплена и отправлена в origin/main: `7fac84c`.
Активное дерево содержит реализацию MCP, Codex skill и необходимые компоненты
ASR/таймлайна. Исследовательские переборы, их зависимости и тесты доступны в
истории; исходные аудио, модели и кэши на диске не удалены.

## Поток данных

1. `start_transcription` проверяет локальный файл, mono/stereo и профиль;
   сохраняет хэш аудио, контекст, словарь, версии кода и immutable request.
2. Отдельный worker берёт блокировку GPU, декодирует A/B и общий mono для
   diarization/layout/aligner. Выбирает лектора, маскирует самостоятельные
   реплики остальных спикеров без сдвига времени.
3. На одинаковых чанках работает CTC beam32/bias4. Оригинальные input-тексты
   сохраняются отдельно. Дополнительный greedy Gibbs — только сигнал агенту;
   его формула не является калибровкой beam-гипотезы.
4. Исторический merger собирает измеренные единицы; каждая целая единица
   принадлежит одному comparison segment. Составные единицы не делятся по
   выдуманным временам. Если единица вышла за core, она сохраняется у ближайшего
   сегмента; её исходные границы остаются доступными. Raw input остаётся доступен
   даже при дефекте merger.
5. SQLite хранит сегменты, текущие решения и append-only журнал ревизий.
   Codex читает страницы и соседей, принимает решения или сохраняет вопросы.
   Конкурирующая старая ревизия отклоняется, batch сохраняется целиком либо не
   сохраняется. Результат экспорта читается из согласованного snapshot.
6. Экспорт создаёт версии TXT/MD/SRT/JSON. Незавершённые места блокируют финал;
   явный draft показывает вопросы/альтернативы. SRT имеет сегментные времена.

## Границы v0.2

Локальный stdio, Russian ASR, CTC combination, mono/stereo, один выбранный
лектор. Предметный preset time-series и общий preset general. Skill выполняет
согласование в текущем Codex, а не через дополнительную LLM-службу. Реплики
студентов, пересекающиеся с речью лектора, не разделяются. Привязки speaker ID
к личности между записями нет. Нет автоматического допуска по WER, обучения,
динамических смесей каналов или обязательного прослушивания агентом.

Получение клипа возвращает локальный WAV-путь. Для другого host нужен доступ к
файлам этой машины; remote HTTP/upload в v0.2 не реализован. Проектная MCP-конфигурация
и skill доступны в Codex, запущенном внутри репозитория. Их можно отдельно
зарегистрировать для другого workspace.

`get_segments(reverse_order=true)` переставляет presentation A/B, сохраняя
идентичности и решения. Это инфраструктура для будущего измерения order bias;
текстовая LLM-инвариантность пока не доказана. Автосогласование применяется
только к буквально одинаковым текстам; агент всё равно может править общие
ошибки с основанием или задавать вопросы.

## Проверка

86 тест прошёл; новый runtime и сервер проходят Ruff, skill прошёл
quick_validate. Проверены сборка package, JSON-RPC stdio MCP и чтение workflow
resource. На 12-секундном stereo-фрагменте R004 выполнены настоящие diarization,
CTC A/B, confidence и aligner на CUDA. Получены «из стационарных» в A и
«нестационарных» в B. Через MCP сохранён вопрос, экспортирован черновик,
переподключён клиент, вопрос прочитан и сохранён выбор B на основании ранее
подтверждённого пользователем эталона R004. Затем экспортированы финальные
TXT/MD/SRT и audit. Это проверка протокола и происхождения решений, не новый
слепой тест и не оценка качества автономного LLM-редактирования.

Дальше измерять Left/Right, LLM(A), LLM(B), LLM(A+B) на одинаковой выборке с
проверкой перестановки источников, пропусков, новых ошибочных правок, чисел и
отрицаний. Для независимой проверки нужны новые эталоны и разнообразное
расположение диктофона. Текущие R/S уже просмотрены.

Официальные интерфейсы: [Codex MCP](https://developers.openai.com/codex/mcp),
[Codex skills](https://developers.openai.com/codex/skills),
[Python MCP SDK](https://github.com/modelcontextprotocol/python-sdk).

Дополнительно проверено: задание, запущенное через MCP, завершает CUDA-обработку
после отключения клиента. Все загрузчики сначала используют готовые локальные
веса, без HEAD/API-запроса к Hugging Face; сеть нужна только для недостающих файлов.
Хэши кода и lock-файлов проверяются также перед отдельными model-worker этапами.
